### (1) SOLID 각각에 대해
- Single Responsibility Principle
  - 단일 책임의 원칙으로, 객체는 단 하나의 책임을 가져야 합니다.
  - 재사용성, 응집도를 높일 수 있습니다.
  - 하지만 산탄총 수술같이 하나의 책임이 여러 클래스에 분산되어 있는 문제가 생길 수 있습니다.
  
- Open Closed Principle
  - 개방폐쇄 원칙으로, 변경에는 닫혀있고 확장에는 열려있어야 합니다.
  - 기존의 코드 변경 없이 기능을 추가할 수 있도록 설계해야 합니다.
  - 단순 상속이 아닌 유지보수성을 생각하며 부모 클래스를 추상화하여 변경하지 못하게 하고, 자식 클래스에서 확장을 통해 변경합니다.

- Liskov's Substitution Principle
  - 서브 타입은 언제나 기반 타입을 대체할 수 있어야 합니다.
  - 기반 타입이 약속한 규약을 지켜야 합니다.
  - LSP는 기능의 명세 즉, 계약과 규약에 대한 내용입니다.
  - 또한 확장에 대한 것으로 LSP를 어기면 OCP를 지킬 수 없습니다.


- Interface Segregation Principle
  - 인터페이스를 클라이언트에 특화되도록 분리시키는 설계 원칙입니다.
  - 클라이언트 관점에서 클라이언트 본인이 이용하지 않는 기능에는 영향을 받지 않아야 합니다.
  - SRP에 따라 단일 책임을 가지는 여러 클래스로 분할하고 각자의 인터페이스를 제공한다면 ISP도 만족할 수 있습니다.

- Dependency Inversion Principle
  - 의존 관계를 맺을 때 변화하기 쉬운 것 또는 자주 변화는것 보다는 변화하기 어려운 것 변화가 없는 것에 의존하는 원칙입니다.

- 최종적으로 SOLID는 변화에 유연하게 대처하는 설계 원칙으로 사용자 관점에서의 설계를 지향합니다.


### (2) Strategy Pattern
- 전략 패턴은 전략을 쉽게 바꿀 수 있도록 해주는 디자인 패턴으로 
- 전략이란, 어떤 목적을 달성하기 위해 일을 수행하는 방식, 비지니스 규칙, 문제 해결 알고리즘 등을 말합니다.

- 기존의 클래스에 정의되어 있는 방법을 수정하려고 기존 코드를 수정하는 것은 OCP를 위배하는것.
- 자주 바뀌는 부분을 추상화하기 위해 클래스로 캡슐화를 진행
- 꼭 interface로 덜어낼 필요는 없고, 전략이 자주 바뀌는 부분을 덜어내서 캡슐화를 진행합니다.
- 상속보다는 위임을 사용합니다.

### (3) Command Pattern
- 기존의 기능에서 변경이 필요할 때 코드 수정을 하게되면 OCP를 위반하게 됩니다.
- 따라서 수행될 기능(명령)을 캡슐화합니다.
- 기능을 요구하는 호출자 클래스(Invoker)와 실제 기능을 수행하는 수신자 클래스(Reciever) 사이의 의존성을 제거합니다.
- 따라서 실행될 기능의 변경에도 호출자 클래스를 수정없이 그대로 사용할 수 있게 해줍니다.

### (4) Template Method Pattern
- 객체의 연산에는 알고리즘의 뼈대만을 정의하고, 각 단계에서 수행할 구체적인 처리는 하위 클래스 쪽으로 미룬다.
- 알고리즘의 구조 자체는 놔둔 채 알고리즘의 각 단계 처리는 하위 클래스에서 재정의 할 수 있게 한다.
- 전체적인 알고리즘을 구현하면서 상이한 부분은 하위 클래스에서 구현할 수 있도록 해주는 디자인 패턴

### (5) Singleton Pattern
 - 싱글턴 패턴이란 인스턴스가 오직 하나만 생성되는 것을 보장하고, 어디에서든 이 인스턴스에 접근할 수 있도록 하는 패턴입니다.
 - 하나의 인스턴스만을 생성하는 책임이 있으며, getInstance 메서드를 통해 모든 클라이언트에게 동일한 인스턴스를 반환하는 작업을 수행합니다.

### (6) State Pattern
 - 상태를 캡슐화로 처리하는 방법
 - 추가되는 새로운 상태에 따라 행위가 달라짐
   - 새로운 상태 추가 → 모든 메소드에 새로운 상태에 따른 행위 추가 → OCP 위배
 - 상태(상태에 의존적인 행위들 포함)를 캡슐화
 - 상태 객체를 Singleton Pattern을 적용시켜 한번만 생성
 - 결론 : 상태에 따라 동일한 작업이 다른 방식으로 실행될 때 해당 상태가 작업을 수행하도록 위임하는 디자인 패턴

### (7) Observer Pattern
 - 데이터의 변화를 통보하는 방법
 - 객체 사이의 일 대 다의 의존 관계를 정의해 두고,
   어떤 객체의 상태가 변할 때, 그 객체에 의존성을 가진 다른 객체들이 그 변화를 통지받고 자동으로 갱신

### (8) Decorator Pattern
 - 여러가지 추가 기능을 조합해야 하는 경우
   - 상속을 통한 기능의 확장은 각 기능별로 클래스 추가해야 함
 - 추가 기능별로 개별적인 클래스를 설계하고 이를 조합
   - 가장 기본적인 기능과 그것을 꾸며주는 기능을 서로 완전히 분리
 - 프로그램 실행중에 특정 객체에게 추가적인 책임들을 동적으로 할당할 수 있다, 기능을 확장할 때 기존 클래스를 상속받지 않고 문제를 해결할 때 사용한다.
  - 다른 객체에게 영향을 주지 않으면서 특정 객체들의 책임을 프로그램 실행중에 추가하여 확장하고 싶을 때 Decorator 패턴을 사용하면 보다 유연하게 기능을 확장할 수 있다.

### (9) Composite Pattern
 - 전체 - 부분의 관계를 가지는 객체들 간의 관계를 정의할 때 유용.
 - 부분과 전체의 계층을 표현하기 위해 객체들을 모아 트리 구조로 구성.
 - 사용자로 하여금 개별 객체와 복합 객체를 모두 동일하게 다룰 수 있도록 하는 패턴

 ### (10) Factory Method Pattern
  - 현재 처리하고 있는 전략과 다른 스케쥴링 전략 사용?
    - 프로그램 실행중에 변경을 해야 한다면? 동적 스케쥴링을 지원해야 한다면?
  - 객체를 생성하기 위해 인터페이스를 정의하지만, 어떤 클래스의 인스턴스를 생성할 지에 대한 결정은 서브클래스가 내리도록 한다.
   - 객체를 생성하는 인터페이스를 따로 정의
   - 생성되는 객체 클래스 결정은 하위 클래스에서 담당
   - 어떤 클래스가 객체를 생성하는 일을 하위 클래스에게 위임
